= ADR-010: Duplicidade de prestador tratada via unique index e MongoServerError
:date: 2026-05-18
:status: Accepted

== Contexto

Um cliente pode ter no máximo um perfil de prestador — a relação é 1 para 1.
Surgiu a questão de onde tratar a tentativa de cadastro duplicado: no domínio
(verificando existência antes de inserir) ou na infraestrutura (via restrição
do banco de dados).

Verificar existência no domínio exigiria uma query adicional a cada cadastro,
mesmo nos casos — a maioria — em que não há duplicata.

== Decisão

A unicidade é garantida por `unique: true` no campo `id_cliente` do
`PrestadorSchema`. Quando há violação, o MongoDB lança um `MongoServerError`
com código `11000`, que é capturado no `errorHandler` e convertido em uma
resposta 422 com mensagem amigável ao cliente.

O nome da collection foi definido explicitamente como `"prestadores"` para
evitar a pluralização automática em inglês feita pelo Mongoose.

== Consequências

* Nenhuma query adicional é feita para verificar duplicidade — o banco garante
a restrição de forma eficiente via índice.
* O `errorHandler` passa a conhecer `MongoServerError`, introduzindo uma
dependência da infraestrutura na camada HTTP. Isso é aceitável pois o
middleware já pertence à camada HTTP.
* Se novos campos precisarem de unicidade, o mesmo padrão deve ser seguido:
`unique: true` no schema e tratamento do código `11000` no handler.
* A mensagem retornada ao cliente é genérica (`'Este cadastro já existe.'`)
para não expor detalhes internos do banco.
== Atualização (2026-11-11): mensagem específica por índice

A avaliação passou a ser bidirecional (cliente → prestador e prestador → cliente), com no
máximo uma avaliação por contrato *e direção*. A mensagem genérica (`'Este cadastro já existe.'`)
não diz ao usuário o que aconteceu, então o padrão foi estendido — sem abandonar a decisão
original de *só índice, sem consulta prévia*:

* A unicidade continua garantida só pelo banco: índice único composto
`{ id_contrato: 1, autor: 1 }` em `avaliacoes` (o `unique` isolado de `id_contrato` foi
removido). O use-case `cadastrar-avaliacao` não consulta se já existe avaliação.
* O índice recebe um *nome explícito* no schema (`name: 'avaliacao_contrato_autor_unico'`,
exportado como constante pelo model).
* O `errorHandler` extrai o nome do índice violado da mensagem do E11000
(`... index: <nome> dup key: ...`) e consulta um mapa `nome do índice -> mensagem`
(`'Você já avaliou este contrato.'`). Índices não mapeados continuam com a mensagem genérica.

Consequências adicionais:

* Para dar mensagem específica a um índice novo: dar `name` explícito no schema e adicionar
a entrada no mapa do `errorHandler`. Índices sem nome continuam funcionando com a genérica.
* O `errorHandler` passa a importar a constante com o nome do índice do model (camada de
infraestrutura), ampliando a dependência HTTP -> infra já aceita acima. A alternativa — repetir o
nome como texto solto — quebraria em silêncio se o índice fosse renomeado.
* A extração depende do formato da mensagem do E11000. Um teste de integração gera o erro num
MongoDB real (`mongodb-memory-server`) e confere a mensagem traduzida, para detectar mudança de
formato numa atualização do MongoDB.
