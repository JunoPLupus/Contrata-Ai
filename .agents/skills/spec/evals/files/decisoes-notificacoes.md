# Decisões fechadas — Notificações (item 8 da remodelagem)

> Arquivo de apoio do cenário 2 dos testes da skill `spec`. Copiado das notas de decisão do projeto
> (conversa de 2026-10-13). Ainda não implementado.

- **8a — Notificações, destinatário (revisado no 8d-ii):** só `id_destinatario` (id do perfil cliente OU prestador), sem `ref` fixo e **sem `tipo_destinatario`** — ObjectId é único no banco todo, e nenhum padrão de acesso atual precisa do tipo (listar, marcar como lida e rotular o perfil se resolvem comparando com os ids do token; `mensagem` já vem pronta). Adicionar depois é barato (TTL limpa as antigas, quase sem backfill). Corrige o DBML, que aponta `id_destinatario` para `usuarios`.
- **8a-ii — VO compartilhado de papel:** opção A — um único `const Papel` (`'cliente'|'prestador'`) + VO em `value-objects/shared/`, recebendo o nome do campo no construtor (como `StringValueObject`). Por ora usado só pelo `autor` (avaliação), já que `tipo_destinatario` foi removido. Refina o 1a. Admin/suporte não é papel desta API.
- **8b-i — Notificações, tipo:** opção A — campo `tipo` = **evento granular** (ex.: `orcamento_recebido`, `orcamento_aceito`, `contrato_concluido`, `avaliacao_recebida`…), VO no padrão dos status. Substitui `tipo_mensagem` do DBML (que misturava canal × evento). Lista de eventos cresce conforme cada use-case passa a notificar. **Canal** não vira campo no MVP (só in-app); entra como campo próprio/coleção de envios quando houver email/push.
- **8b-ii — Notificações, texto:** opção A — `mensagem: String` com **texto pronto**, montado no backend na criação a partir de um modelo de texto por `tipo`. Semântica de "foto do momento" (registro de evento passado); estado atual se vê pelo recurso referenciado (8c). Descartados: montar no front (N+1 de consultas) e objeto `dados` livre (campo sem formato fixo).
- **8c — Notificações, ligação com o recurso:** opção A — só `id_referencia` (opcional). O tipo do recurso é derivado do `tipo` (evento granular), sem `tipo_referencia`. Mapa `tipo → rota` fica no front (sem link pronto no backend). Para cada evento, apontar para onde faz sentido o destinatário ir (ex.: `orcamento_recebido` → solicitação).
- **8d-i — Notificações, leitura:** opção B — `data_leitura: Date` opcional (ausente/`null` = não lida), no lugar de `lida: Boolean`. Justificativa: **índice TTL** do MongoDB apaga automaticamente notificações lidas após N dias (não lidas nunca expiram, pois não têm data). Prazo N a definir. A data de criação continua existindo (nome tratado no 8d-ii).
- **8d-ii — Notificações, índices/datas:** data de criação = `data_criacao` (padrão de avaliação/orçamento; DBML usava `data`). Índices opção A (enxuto): `{ id_destinatario: 1, data_criacao: -1 }` + TTL de campo único em `{ data_leitura: 1 }`. ObjectId é único no banco todo, então `tipo_destinatario` não precisa estar no índice.
- **8d-iii — Notificações, prazo do TTL:** **30 dias** após `data_leitura`, guardado numa **constante nomeada** (não número solto no model). Atenção: o Mongoose não atualiza `expireAfterSeconds` de índice já existente — mudar depois exige `collMod` ou recriar o índice.
- **8e — Notificações, geração:** opção B — **serviço de notificação** com abstração no domínio (classe abstrata, ex.: `INotificador`, no padrão dos repositórios) e implementação injetada pelo container. Use-cases chamam algo como `notificar(tipo, idDestinatario, idReferencia, dadosDoTexto)`; o serviço monta a `mensagem` (modelos de texto centralizados por `tipo`) e persiste. Canal futuro (email) entra dentro do serviço sem tocar nos use-cases. Descartados: repositório direto em cada use-case (texto espalhado) e eventos/EventEmitter (exagero no MVP; migração B→C é simples se precisar).
- **8e-ii — Notificações, falha:** opção C — **melhor esforço**: try/catch **dentro da implementação do serviço**; não propaga erro ao usuário. Contrato da abstração documenta "`notificar` nunca lança". Chamar `notificar` **depois** que a operação principal foi gravada com sucesso. **Log obrigatório**: no MVP local (console), mas atrás de uma **abstração de logger** (classe abstrata, ex.: `ILogger`, injetada pelo container) para plugar Sentry ou outra plataforma depois trocando só a implementação. Hoje não há logger na API (só `console.error` no `server.ts`). Descartados: propagar (usuário vê erro de algo que já foi feito) e transação (invasivo, exige replica set).
- ✅ **Item 8 (Notificações) fechado.** Forma final: `notificacoes { id_destinatario, tipo, mensagem, id_referencia?, data_criacao, data_leitura? }`.

- **Triagem (2026-10-13):** "excluir notificações lidas" **entra no MVP** (rota com `deleteMany`, acionada pelo próprio usuário, sem custo de modelagem).
